# 気づきワードサイクル Phase 3 スライス2 — Pamunモニターシグナル取込（購買意向共感率の自動化） 設計仕様書

作成日: 2026-07-16
ステータス: 設計確定（実装計画はこの後 writing-plans で作成）
位置づけ: Phase 3 の2番目のスライス。訴求スコア25点を占める「購買意向共感率」を自動化し、確度ステージ「レビュー反映」を機械で立てられるようにする。

## 背景・狙い

Phase 1（[score.js](../../../lib/kizuki/score.js)）／Phase 2（[ledger-store.js](../../../lib/kizuki/ledger-store.js)）／Phase 3 スライス1（[ad-ingest.js](../../../lib/kizuki/ad-ingest.js)）を土台に、これまで手入力だった「モニターシグナル」＝**購買意向共感率（25点）** を Pamun 施策データから取込む。

### 実データ調査で判明した前提（2026-07-16・実レポート2本を確認）

調査対象: `《2026_04_スターダストグロウエッセンス》施策レポート.xlsx` / `《2026_06_ブラッシュオンUVパウダー》施策レポート.xlsx`

現行の施策レポート（1商品1ファイル）のシート構成:

| シート | 中身 | 本スライスでの扱い |
|---|---|---|
| 投稿集計 | 1行=1モニター、列=媒体別（IG/LIPS/@cosme/X/Blog/Lemon8/モノシル/Threads/TikTok/その他）の**投稿URL**。上部に商品名・商品ページURL・媒体レビュー状況・備考 | **使わない**（URLの束のみ。中身はリンク先を開かないと取れない）。突合は後続スライス |
| **《事後アンケート》詳細** | 1行=1回答者。`ご年齢` / `①商品の満足度` / `②商品の良かった点`(自由記述) / `③商品の改善点`(自由記述) / `④容器であったら嬉しい商品` / `⑤一番気に入ったもの` | **唯一の構造化入力**（04ファイル=50人） |
| 《アンケート》集計結果 | `集計人数` / `回答平均年齢` のみ | **n（全回答者）の取得元** |
| 《事前アンケート》詳細 | 06ファイルに存在するが空 | 現状未運用。使わない |
| 空白詰め / 複数のURLが同じセル内に | 作業用シート（`#VALUE!`・`#N/A` を含む） | 使わない |

**構造的なギャップ（本スライスが解く問題）**:

- **word_id が存在しない** — 設問が「商品全体」への質問で、気づきワード単位になっていない
- **購買意向を直接聞く設問がない** — ①満足度は「満足 ≠ 買いたい」。気づきの言語は②良かった点の自由記述に埋まっているが非構造
- **媒体レビュー状況（「★4.21/5（119件）」等）は媒体全体の全ユーザー評価**であり、モニター限定ではない → **共感率の分母に混ぜると汚染する**（「虚栄に騙されない」原則に反する）。本スライスでは使わない
- **「レビュー件数」の定義が二重**（投稿数103件／回答者数50人／word_id別の共感数）→ 本仕様で確定させる（後述）

## 確定した設計方針

- **ハイブリッド2トラック**。「気づきワードサイクル用の新Pamun進行」はアンケートを標準化できる（Track A）が、「既存の従来Pamun進行」は現行フォーマットのまま来る（Track B）。両方を同じ出力に合流させる
- **両トラックとも出力は同一のモニターシグナル行**。upsert → `ledger-store` 再計算という**スライス1と同じ経路**に合流（新経路を作らない）
- **`score.js` は不改変**（単一の正を維持）。`ledger-store.js` の review 集約のみ「source優先ピック」に変更
- **共感率の分母＝全回答者 n に統一（＝普及率）**。ワードに言及しなかった人も「意向なし」として分母に残す。これにより Track A/B で数字の意味が揃い、ボリュームも反映される
- **LLM分類は閉じた集合への写像のみ**（新語を生成しない）。マッピング外はスキップ＝スライス1の思想と同一（虚栄インフレ防止）
- **純粋関数が唯一のロジック核**（`review-ingest.js`）。LLM呼び出し等の副作用は `scripts/` 側に置き、変換は決定的でテスト可能に保つ

## 用語・フィールドの確定定義

| フィールド | 定義 | score.js が消費するか |
|---|---|---|
| **n（全回答者）** | その施策のモニターアンケート全回答者数（例: 50人）。施策メタ。取込時に率を確定計算するのに使う（行には持たない） | — |
| **レビュー件数(word_id)** | そのワードに**共感/言及した人数**（Track A=②③選択者、Track B=言及者） | **しない**（件数・確度の目安／台帳UI表示用） |
| **購買意向共感率(word_id)** | **「買いたい/使い続けたい」人数 ÷ n**。台帳へは `"62%"` 形式で書き、`parseReviewRow` が `/100` して 0..1 にする（Phase 2 の既存挙動のまま） | **する**（25点） |

この定義により、**多くが共感したが誰も買わない「虚栄ワード」は、件数は高いが共感率は低く出る**（例: 「パケが可愛い」）。設計仕様書 `2026-06-30-kizuki-word-cycle-design.md` の虚栄控除の思想と一致する。

## アーキテクチャ／データフロー

```
Track A（新・気づきワードサイクル進行）※クリーン・決定的
  気づきワード台帳(case) ──候補ワード5〜8件を引く──▶ Pamunアンケート「気づきワード確認セクション」を生成
     │ 各ワードを1問3択で聞く（設問がそのまま word_id 単位＝生まれつきの紐付け）
     ▼ 回答（word_id付き・LLM不要）
  集計: 件数=②③選択者 / 意向=③選択者 / 共感率=③÷n                        ─┐
                                                                              │
Track B（既存の従来進行）※ベストエフォート・要レビュー                        │
  現行レポート《事後アンケート》詳細（②良かった点 等 自由記述）                │
     │ ① Pamun取込マッピング（report/施策名 ↔ caseId）で候補ワード集合と n を引く
     │ ② LLMで各回答を「台帳候補ワード（閉じた集合）」に写像
     │    → { word_id, intent: yes/no, vanity: bool, confidence }（新語は生成せず「該当なし」に逃がす）
     ▼ ③ 集計: 件数=言及者数 / 共感率=意向あり÷n（vanityのみの反応は意向に数えない）
                                                                              │
                                                                              ▼
  review-ingest：{分類結果 + n} → モニターシグナル行（source/campaign_id/confidence 付き・%文字列化）
     │ ④ 「モニターシグナル」タブを (word_id, campaign_id, source) で upsert（手入力/上位トラックは不可侵）
     ▼
  recalc：ledger-store で全シグナル集約（review は source優先ピック）→ computeAppealScore → 台帳へ書戻し
     ▼
  気づきワード台帳（Sheets）→ コックピット表示（Phase 2）
```

## Track A：標準化アンケートの設問形

台帳(case)の候補気づきワードを引き、**各ワードを1問3択**で聞く。

> **Q. 「〇〇（気づきワードの言い回し）」について、あなたに一番近いものは？**
> 1. ピンとこない／当てはまらない … 分母のみ
> 2. 共感する（でも購入の決め手ではない） … 件数 +1、意向 0 ＝ **虚栄反応の受け皿**
> 3. 共感するし、**これがあるから買いたい／使い続けたい** … 件数 +1、意向 +1

- **集計は決定的（LLM不要）**: 件数 = ②③、意向 = ③、共感率 = ③ ÷ n
- 「虚栄反応は除外」が**設問構造で担保**される（可愛い等は②に落ち③に上がらない）
- **候補ワードは5〜8件に制限**（設問数＝ワード数のため、超えると回答負担で離脱する）。台帳から引く際に上限を強制する

## Track B：LLM分類の契約

- **入力**: 1回答者ぶんの `{ age, satisfaction(①), goodPoints(②), improvements(③), favorite(⑤) }` ＋ その case の候補ワード一覧
- **出力**: `[{ word_id, intent: boolean, vanity: boolean, confidence: number }]`（0件＝該当なし可）
- **制約**:
  - `word_id` は**与えられた候補一覧のいずれかのみ**（新語生成禁止・該当なしは空配列）
  - `intent` は「買いたい／使い続けたい」に相当する記述がある場合のみ true（満足の表明だけでは false）
  - `vanity=true`（見た目・パッケージ等の反応のみ）は **intent に数えない**
- 主入力は `②良かった点`。`①満足度`・`⑤一番気に入った`は文脈として渡す（`③改善点` はネガティブ判定の文脈用）

## データモデル

### Sheet: 「Pamun取込マッピング」タブ（新規・コックピットの SHEET_ID）

**Track B 専用**。スライス1の「広告マッピング」と同じ役割＝**自動管理の許可リスト**で、ここに無いレポートは取込まない。
（Track A は台帳から設問を生成するため `case_id` / `campaign_id` / `n` を自前で持っており、この表を必要としない）

| 列 | 内容 |
|---|---|
| `campaign_id` | 施策の一意キー（例: `2026_04_stardust`） |
| `report_name` | レポート識別（ファイル名／施策名） |
| `case_id` | 台帳の case（候補ワード集合を引くキー） |
| `n` | 全回答者数（《アンケート》集計結果の `集計人数`。取込時に読めれば自動、手入力も可） |

### Sheet: 「モニターシグナル」タブ（**Phase 2 schema を3列拡張**）

```
[word_id, レビュー件数, 購買意向共感率, 代表URL, 2次利用可否, source, campaign_id, confidence]
 r[0]     r[1]          r[2]             r[3]     r[4]          r[5]    r[6]         r[7]
                                                  └──────── 追加（スライス1が creative_id を足したのと同じ）
```

- `source` ∈ `{ manual, trackA, trackB }`
- **upsertキー = (word_id, campaign_id, source)**
- `confidence` = trackB のみ有効（0..1）。trackA/manual は空
- **既存の `parseReviewRow` は r[0]/r[2] しか読まないため後方互換**（追加列は末尾＝既存行はそのまま動く）
- `代表URL`・`2次利用可否` は当面**手入力/任意**（投稿集計との突合は後続スライス）

### 合流時の優先順位（`ledger-store.js` の変更点）

現在の `aggregateSignals` は review の `intentRate` を**単純平均**している（`ledger-store.js:81`）。クリーンな trackA と機械生成の trackB を平均するのは不正なので、**source優先ピック**に変更する:

```
trackA > manual > trackB   （採用は最優先sourceのみ。ブレンドしない）
同一source内に複数行（複数campaign）→ 従来どおり平均
```

`score.js` は不改変。変更は `ledger-store.js` の review 集約のみ。

## テスト方針

- **`review-ingest.js` のユニットテストが本体**（純粋関数・決定的）:
  - 共感率 = 意向 ÷ n（**言及なしは分母に残る**＝普及率であることを固定するテスト）
  - vanity=true が意向に数えられない
  - n=0 → 率は null（0除算防止。`ad-ingest.js` の `pctStr` と同じ扱い）
  - 件数 = 共感/言及者数（意向数ではない）
  - `"62%"` 形式の文字列化（小数1桁・`pctStr` と整合）
  - 候補外 word_id はスキップ
- **`ledger-store` の source優先ピック**: trackA と trackB が同一word_idにある → trackA のみ採用（平均しない）
- 実レポート2本（04/06）を fixture 化した結合検証（`parseAdRow` 結合検証と同じ思想）。06は事後アンケート空＝**n=0/空データで落ちない**ことの回帰テストとして価値が高い
- 既存 102 テストは全て維持

## スコープ外（後続スライス／別spec）

- **投稿集計URLの中身の取得**（キャプション/画像のクロール・二次利用可否の自動判定）→ 代表URL自動化は別スライス
- 媒体レビュー状況（★4.21/5 等）の取込 — 分母が汚染されるため本スライスでは意図的に使わない
- 事前アンケート（現状未運用）
- 台帳の BigQuery 昇格＋Looker 可視化 → スライス3
- 他媒体（Meta等）広告コネクタ

## オープン論点（実装時に確定）

- **レポートの入力経路**: xlsx直読み（現状の受領形態）か、Google Sheets化してSheets API か。まず xlsx 直読みで立ち上げ、運用が固まったらSheets統一を検討
- **LLMモデル/呼び出し単位**: 回答者1件ずつか、バッチか（コストと精度のトレードオフ）
- **confidence の閾値**: 何未満を「要レビュー」バッジにするか。初期は全trackB行にバッジを出す運用で開始し、実データで調整
- **trackB → manual 昇格のUI**: コックピット上でレビュー→採用する導線（Phase 2 のタブに追加）
