## 1. 背景と課題（実データで判明）

本番で「候補を提案してもらう」を実行したところ **27件** が提案された（P1完了）。
ただし精査の結果、以下が判明した。

1. **中核カテゴリが一度も検索されていなかった。**
   `discover_tiktok.js` の `--max-seeds=12`（コスト上限）が先頭12シードで打ち切り、
   Notionの返却順で後ろに回った **コスメ・スキンケア・ヘアケア・ボディケア・フレグランス** が
   毎回まるごとスキップされていた（＝Trepoの主戦場が空白）。
2. **切り捨てはサイレントではないがカテゴリ単位で偏る。** 現状の `discover.js` はONシードの
   ハッシュタグを1つのフラットな集合に潰して渡すため、どの12個が走るかは順序依存で非決定的。
3. **種そのものは全カテゴリで優秀。** 未実行だった美容10シードを検証実行したところ、
   ロムアンド／キャンメイク／fwee／ミジャンセン／ケラスターゼ／Dior／アドバンスドクリニカルズ 等
   **13件の良質候補**が出た（`#新作コスメ`→ロムアンド, `#ヘアオイル`→ケラスターゼ 等）。
   → **質の問題ではなくカバレッジの問題。**
4. **コストは非ボトルネック。** Apify実測 $0.046 / 月上限 $29。1シード≒数秒・1〜2セント/回。
5. **真の制約は「時間」。** 12シードの本番実行で **約7分**（POST 01:46:08 → 最終ポーリング 01:53:03）。
   Cloud Runの発掘ジョブは「HTTPレスポンス後の非同期・タブを開いている間だけ生存」なので、
   全29シードを一度に回すと15分前後になり、**インスタンス回収／タブ閉じで結果が消えるリスク**が高い。

## 2. ゴール

- **カバレッジ**: 1回の実行で **すべてのONカテゴリが必ず1つ以上検索される**。中核カテゴリが空白にならない。
- **時間**: 1回の実行を **実証済みの約7〜8分の範囲（≒14シード）** に収める。
- **育てても壊れない**: シードが増えても1回の実行時間は一定。増えた分はローテーションで次回に回る。
- **質の継続改善**: シードの追加・更新を回す運用（SOP＋フィードバックループ）を明文化する。
- **非破壊の原則を維持**: 発掘→精選→**提案**まで。DB登録は承認後のみ（P1の設計を変えない）。

## 3. 方針（採用案）

「毎回全シードを回す」は**却下**（時間超過リスク）。
**カテゴリ均等・1回あたり上限付き・超過分は次回ローテーション** を採用する。

### 3.1 選定アルゴリズム（`lib/discover.js` に実装）

純粋関数として実装し、ネットワークなしで単体テスト可能にする。

入力: `categoryTags: Map<category, string[]>`（ONシードから構築）、`cap`（既定14）、`rotation`（整数）
出力: `selected: {tag, category}[]`（最大 `cap` 件）

手順:
1. ONシードから **カテゴリ→ハッシュタグ配列** を作る（フラット化しない）。タグ空のカテゴリ（例: 「その他」）は除外。カテゴリ内・カテゴリ間の重複タグは除外。
2. **ラウンドロビンで層状に選ぶ**:
   - ラウンド1: 各カテゴリから1つずつ（＝全カテゴリを必ず代表。カテゴリ数 ≤ cap を前提）。
   - ラウンド2以降: `cap` に達するまで、各カテゴリの次のタグを順に追加。
   - 各カテゴリ内で「何番目のタグを先頭にするか」は `rotation` でずらす: `tags[(rotation + i) % tags.length]`。
3. `cap` 到達で打ち切り。**選ばれたタグ／今回見送ったタグ** をログに出す（サイレント切り捨て禁止）。

**ローテーションはステートレス**にする（Cloud Runはインスタンス間で状態を持たない）。
`rotation = 起点からの経過日数`（サーバーの `Date` で算出。ワークフロー実行ではなく通常のExpressサーバー上なので `Date` 使用可）。
→ 日が変われば各カテゴリの先頭タグがずれ、数回の実行で全タグが一巡する。同日中の再実行は同じ選定（許容）。

> 補足: より厳密な巡回が必要になったら、Notionシード設定DBに「最終発掘日」列を持たせてカーソル管理に
> 差し替え可能。v1ではステートレス日次ローテーションで十分（YAGNI）。

### 3.2 実行フロー（変更後の `proposeCandidates`）

```
listSeeds()                                   … Notionから取得（既存）
  ↓ カテゴリ→タグMap構築（フラット化を廃止）
selectSeeds(map, cap=14, rotation=経過日数)     … 3.1のアルゴリズム（新規・純粋関数）
  ↓ selected の tag 配列
discover_tiktok.js <selected tags> --per 30 --top 8 --max-seeds <selected.length>
  ↓ 共起タグ（生）
filter_candidates.js（Claude精選）              … 既存
  ↓ 既存候補・シード自体・重複を除外
提案リストを返す（Notionには書かない）           … 既存（P1のまま）
```

- `--max-seeds` には `selected.length` を渡し、**lib側で件数を制御**（discover_tiktok側のデフォルト12に依存しない）。
- discover_tiktok.js 自体は変更最小（必要なら安全上限のデフォルトを上げるのみ。選定責務はlibに集約）。

### 3.3 ログ（`job.log` に出す＝画面に見える）

- `対象カテゴリ N件 / 今回のシード M件（上限 cap）`
- カテゴリごとの選定タグ一覧
- `今回見送り（次回ローテーション）: [tag...]`（あれば）
- 精選後: `提案 X件（カテゴリ別内訳）`

## 4. シードの質・育て方（Notion運用 ＋ SOP）

コードでなく**運用**で回す部分。SOPをランブックに追記する。

1. **各カテゴリ 2〜4個の具体寄りシード**を持たせる（現状の総称語でも機能しているが、
   カテゴリが痩せている場合に追加）。今回の実測で全カテゴリが機能することは確認済み。
2. **フィードバックループ**（今回は手動運用・自動化は次フェーズ）: 採用された候補ブランドの一部を
   次サイクルのシードに昇格させる（例: 「fwee」が採用 → `#fwee` をコスメのシードに追加）。
   v1は編集部が手でシード設定DBに追記。**次フェーズで方式Aとして半自動化予定**（下記§9）。
3. **定期リフレッシュ**: TikTok Creative Center の急上昇ハッシュタグを月1でシードに反映（既存SOPと接続）。
4. **痩せた種の可視化**: 3.3のカテゴリ別産出ログで、産出ゼロが続くシードを間引く判断材料にする。

## 5. コンポーネントと責務

| 単位 | 責務 | 依存 |
|---|---|---|
| `selectSeeds(map, cap, rotation)` （新規・純粋関数） | カテゴリ均等＋ローテーションでシードを選ぶ | なし（テスト容易） |

| Notion シード設定DB （運用） | シードの単一の真実。編集部が育てる | — |

## 6. テスト

- **`selectSeeds` の単体テスト**（ネットワーク不要、`node --test`）:
  - 全カテゴリが必ず1つ以上含まれる（カテゴリ数 ≤ cap のとき）。
  - `cap` を超えない。
  - タグ空カテゴリを除外する。
  - カテゴリ内/間の重複タグを除外する。
  - `rotation` を変えると各カテゴリの先頭タグがずれる。
  - `rotation` が同じなら結果が決定的。
- **結合（手動・実キー）**: 本番相当のシードで `proposeCandidates` を1回流し、
  中核カテゴリ（コスメ等）が提案に含まれることを確認（今日の検証と同等）。

## 7. スコープ外（YAGNI）

- Notionカーソルによる厳密巡回（ステートレス日次で十分）。
- Cloud Scheduler による自動定期実行（Phase 2のBigQuery化とあわせて検討）。
- 発掘ジョブ結果の永続化（タブ閉じ対策）。長時間化を避ける本設計では優先度低。
- 売上/インフル反響シグナルの自動化（別タスク）。
- **フィードバックループの半自動化（§9）— 今回のカバレッジ改修とは切り離し、次フェーズで実装。**

## 8. リスクと対処

| リスク | 対処 |
|---|---|
| カテゴリ数が cap を超えるほど増える | ラウンド1で全カテゴリを入れられなくなる。cap既定14＞現状11で余裕。将来はcap調整 or 巡回。 |
| 同日再実行で同じ提案 | 許容（日次ローテーション）。variety が要るなら手動でシード調整。 |
| discover_tiktok 側のデフォルト12との二重管理 | lib側が明示的に `--max-seeds=selected.length` を渡し、責務をlibに一本化。 |
| 7〜8分の非同期ジョブ中のタブ閉じ | 本設計は実行時間を実証済み範囲に抑えることで軽減。永続化はスコープ外。 |

## 9. 次フェーズ: フィードバックループの半自動化（方式A・別計画）

**今回のカバレッジ改修には含めない。** 全カテゴリが提案に出る状態が実現した後、独立した計画で実装する。

**狙い**: 採用された候補ブランドを次サイクルの種に昇格させ、発掘を自己強化する
（例: 「fwee」採用 → コスメの種に `fwee` を追加 → 次回さらに関連候補が出る）。

**方式A（人が承認）を採用**。本プロジェクトの一貫した思想「DBへの書き込みは人の承認後」に合わせる。
Claudeやコードが勝手にシード設定DBを書き換えない。

**フロー**:
1. 採用（`adoptCandidates`）の後、採用された候補のうち **種に向くもの（ブランド／IPレベル）** を提案として提示。
   - 種に向く: ブランド名・IP・チェーン（共起タグが豊富に出る）。例: fwee, ロムアンド, キャンメイク
   - 種に向かない: 細かすぎる商品名（共起がほぼ出ない）、既に十分メジャーな一般名詞
   - この判定は §3 のClaude精選と同様に **Claudeで候補を分類**し、編集部が最終チェック（＝提案止まり）。
2. 編集部がチェックしたものだけ、該当カテゴリのシード設定DB行の「ハッシュタグ」セルに **追記**（重複は除外）。

**必要な技術改修（いずれも軽微）**:
- `listSeeds()` が各シード行の **ページID** を返すようにする（追記先の特定に必要。現状は返していない）。
- `notion.js` に **シード行のハッシュタグ追記関数**を追加（`createCandidate` と同種のNotion書き込み）。
- フロント: 採用完了後に「次回の種に追加する候補」チェックリスト＋ `POST /api/seeds/promote` 相当。

**非対象**: シードの自動削除・自動書き換え（痩せた種の間引きは §4-4 のログを見て人が判断）。
