**日付:** 2026-07-27

**ステータス:** 設計

## 背景

S2d-1でX候補の受け皿（候補DB・`media=X`）を作り、S2d-2でX転換質診断（Apify＋Claude）を実装・本番デプロイした。

しかし本番投入直後に**機能が起動できない**ことが判明した。候補DBの「X候補を読み込む」を押しても0件で、診断が始められない。

原因は**X候補をDBに入れる経路が「Astream X CSV取込」の1本しかない**こと。AstreamのCSVを持っていなければX候補は永久にゼロで、S2d-2の診断機能は事実上死んでいる。

調査の過程で、もう1つの実装漏れも判明した。「3. 候補を探す」タブの **🔎 YouTube自動検索は結果を表示するだけで、候補DBに登録するボタンが無い**（`registerCand` を呼んでいない）。つまり「探す」タブは探せても貯められない。

本設計はこの2つを埋め、「探す→貯める→診断する」の導線を初めて通す。

## ゴール / 非ゴール

**ゴール**

- キーワード（カテゴリ語・商品/ブランド名）でXアカウントを発掘し、候補DBに登録できる
- 企業公式・懸賞垢・botを自動除外し、除外理由と件数を明示する
- エンゲージ率順に並べ、規模帯によらず「反応されている人」を上に出す
- `📑 Astream X CSV取込` を「4. 診断する」→「3. 候補を探す」へ移設する
- 🔎 YouTube自動検索の結果に「DBに登録」ボタンを追加する

**非ゴール**

- フォロワー規模での自動絞り込み（規模帯は案件ごとに変わるため、一覧に全部出して人間が選ぶ）
- Xの客層（女性%・中核年齢）・実在率の推定（S2d-1の「Xでは構造的に取得不可」という割り切りを継承）
- 発掘と同時に転換質診断を自動実行すること（1件1〜1.5分・コストも乗るため、診断は従来どおり明示操作）
- Astream IG CSV（転換質プロキシ）の移設（あれは転換質を算出する診断機能なので「4. 診断する」に残す）

## Apifyアクター（実地検証済み・2026-07-27）

**`apidojo~tweet-scraper`**（🏯 Tweet Scraper V2 - X / Twitter Scraper）を使う。

S2d-2で使った `apidojo~twitter-profile-scraper` は `twitterHandles` 指定型＝**既にアカウント名を知っている前提**のため、発掘には使えない。検索には別アクターが要る。

実際に叩いて、必要な値がすべて取れることを確認した（`searchTerms:['毛穴ケア'], maxItems:5, sort:'Top', tweetLanguage:'ja'`）。

| 必要なもの | 取得できるフィールド | 実測例 |
|---|---|---|
| 検索 | `searchTerms`（複数可）／`tweetLanguage:'ja'` で日本語限定 | 5件取得成功 |
| アカウント | `author.userName` | `marunouchi__ol_` |
| フォロワー数（率の分母） | `author.followers` | 737,949 |
| エンゲージ指標 | `likeCount` / `retweetCount` / `replyCount` / `viewCount` | like 74,875 / RT 4,533 |
| 除外判定の材料 | `author.description`（プロフィール文）／`author.name`／`isBlueVerified`／`statusesCount` | 取得OK |

**料金:** PAY_PER_EVENT `$0.0004`/ツイート。検索語3語×100件＝300件で約 **$0.12（約18円）**。探索的に何度も回せる水準。

## 決定的フィルタ（`lib/x-account-filter.js`・純粋関数）

### なぜルールベースか（Claude判定を採らない理由）

S2d-2では「懸賞除外はコード、意向判定はClaude」というハイブリッドを採った。本設計の除外も**コード側**に置く。理由は3つ。

1. **検索は探索的に何度も回す。** 語を変えて試すたびにClaude呼び出しが乗ると、コストと1分の待ちが積み上がり、探索という行為自体が成立しなくなる
2. **除外ミスのリスクが診断と違う。** 転換質診断の誤りは「間違った数字を信じる」に直結するが、検索の誤除外は一覧を見れば人間がすぐ気づける
3. **Xの自己紹介は明示率が高い。** 「公式」「Official」「PR」「懸賞」等を名乗る率が高く、ルールで実用十分

### 除外する3種

| 種別 | 判定材料 | 例 |
|---|---|---|
| 企業・ブランド公式 | `author.name` / `description` に「公式」「Official」「株式会社」「\|公式」等 | ブランド公式・販売店 |
| 懸賞・プレゼント垢 | **S2d-2の `isGiveawayPost` を再利用**し、プロフィール文＋ヒットツイートに適用 | 懸賞応募専用アカウント |
| bot・まとめ・ニュース | `name`/`description` の「bot」「まとめ」「速報」「ニュース」＋投稿数の異常値 | 自動投稿・まとめサイト |

### 除外は消さずに「見せる」

S2d-2の `giveawayExcluded` と同じ思想で、**除外したアカウントも件数と理由を返す**。UIは既定で畳んでおき、「除外 N件（公式x / 懸賞y / bot z）」と出す。

これは検索特有の配慮である。S2d-2の除外は「やや過剰でよい」（取りこぼしはバイアスになるが、過剰除外はサンプルが減るだけ）だったが、**検索での過剰除外は候補そのものを失う**。だから捨てずに見せ、誤除外に人間が気づけるようにする。

### 関数

- `isOfficialAccount(author)` → boolean
- `isBotAccount(author)` → boolean
- `classifyAccount(author, tweets)` → `{ excluded: boolean, reason: '公式'|'懸賞'|'bot'|null }`
  - **懸賞の判定基準を明示する:** プロフィール文が懸賞語を含む **または** そのアカウントのヒットツイートの**過半**が `isGiveawayPost` に該当する場合に除外。1件でも懸賞があれば除外、とはしない（たまたま懸賞に反応した一般ユーザーを失うため）
- `engagementRate(avgLike, avgRt, followers)` → number|null
- `aggregateAuthors(tweets)` → 集約済み候補配列

## エンゲージ率の定義

```
エンゲージ率(%) = (平均いいね + 平均RT) ÷ フォロワー数 × 100
```

同一アカウントが検索に複数ヒットした場合は**平均**を取る。

**重み付けはしない**（S2d-2の転換質%と同じ原則）。いいねとRTを1:1で単純合計する以上の恣意的な係数は入れない。未検証の定数は過学習の温床になるため。`like` / `retweet` / `reply` / `view` の**内訳はすべて返す**ので、後から別定義で再集計できる。

**分母の下限ガード:** `followers < 100` のアカウントは率を `null`（表示は「—」）とする。分母が小さすぎて率が爆発し、順位が無意味になるため。除外はしない（一覧には出す）。

**較正スタンス:** このエンゲージ率は**X内の相対比較専用**。YouTube/IGの指標とは較正されていないため、媒体をまたいで並べない。UIにも明記する。

## アーキテクチャ

S2d-2で作った構造をそのまま踏襲する。新しいインフラは増やさない。

```
ブラウザ（3.候補を探す タブ）
   │  POST /api/cockpit/x-discover  { keywords: ["毛穴ケア", "◯◯化粧水"] }
   ▼
cockpit-server.js
   │  runScriptJson（S2d-2で実装済み・再利用）
   ▼
scripts/apify/discover_x.js
   │  apidojo~tweet-scraper（searchTerms・ja・maxItems）
   ▼
lib/x-account-filter.js（純粋関数）
   投稿者ごとに集約 → 3種を除外 → エンゲージ率順
   ▼
一覧表示 → チェック → registerCand({media:'X'}) → 候補DB
                                              ▼
                                    S2d-2のX転換質診断が使える
```

**1リクエストで完結する。** S2d-2の転換質診断は1アカウント1〜1.5分かかるためバッチにできなかったが、検索は300件取得でも数十秒で終わるため、Cloud Runの300秒制限に収まる（`run-sync` タイムアウトは180秒・S2d-2と同値）。

**取得件数:** 検索語1つあたり100件、語は最大3つ（＝最大300件・約18円）。これを既定値とし、UIに明示する。

## データフロー

1. ユーザーがキーワードを入力（改行/カンマ区切り・最大3語）
2. `POST /api/cockpit/x-discover` → `discover_x.js` を起動
3. tweet-scraper で語ごとに最大100件取得（`tweetLanguage:'ja'`, `sort:'Top'`）
4. `aggregateAuthors` で投稿者ごとに集約（ヒット数・平均like/RT・フォロワー）
5. `classifyAccount` で3種を判定 → `included` / `excluded` に振り分け
6. `included` をエンゲージ率降順でソート
7. 一覧表示（除外分は畳んで件数と理由を表示）
8. チェック → 「DBに登録」→ 既存 `registerCand({account, media:'X', followers, prEngage})`

**エンゲージ率の格納先は `prEngage`（候補DBの「PRエンゲージ%」列）とする。** 新しい列は追加しない。既存の `📑 Astream X CSV取込` が同じ列にX候補のエンゲージ率を入れており（`prEngage: r.engageRate`）、それに揃える。列名は「PRエンゲージ%」だが、X候補では一般投稿のエンゲージ率が入る点は既存挙動と同じで、ここで意味を変えない。

## エラーハンドリング

S2d-2と同じ方針で、**段ごとに切り分けて返す**（どこで失敗したか運用者が分かるように）。

| 状況 | 挙動 |
|---|---|
| `APIFY_TOKEN` 未設定 | 400 `APIFY_TOKEN未設定（Cloud Runの環境変数に追加してください）` |
| キーワード未入力 | 400 `キーワードを入力してください` |
| 検索語が4つ以上 | 400 `キーワードは3つまでです` |
| Apify呼び出し失敗 | 502＋Apifyのエラー内容を添える |
| ヒット0件 | 200／`candidates:[]`＋`note:'該当ツイートなし（語を変えてください）'` |
| 全件が除外対象 | 200／`candidates:[]`＋除外内訳を返す（「0件」と「全部除外」を区別する） |
| フォロワー0/極小 | 率を `null` にして一覧には出す（除外しない） |

## テスト方針

**単体テスト（`node:test`）— `lib/x-account-filter.js`**

- `isOfficialAccount`: 「公式」「Official」「株式会社」を含む名前/プロフィールを検出、一般ユーザーは誤検出しない
- `isBotAccount`: 「bot」「まとめ」「速報」を検出
- 懸賞判定: S2d-2の `isGiveawayPost` がプロフィール文にも効くこと
- `aggregateAuthors`: 同一アカウントの複数ツイートが1件に集約され、平均が正しいこと
- `engagementRate`: 通常計算／`followers<100` で `null`／`followers=0` でゼロ除算しないこと
- ソート: エンゲージ率降順、`null` は末尾

**手動確認（デプロイ後）**

- 実キーワードで検索し、企業公式が上位に居座らないこと
- 除外内訳が表示され、誤除外が無いか目視できること
- 登録した候補が候補DBに入り、S2d-2のX転換質診断で読み込めること（＝導線が繋がったことの確認）

## 情報設計の変更

**① `📑 Astream X CSV取込` を「3. 候補を探す」へ移設**
このカードは転換質を算出せず、候補をDBに入れるだけ。「探す」の仕事なので移す。カードの中身（`asxcsv` input・`runXIngest`）は変更しない。

**② `📑 Astream CSV → IG転換質プロキシ / マスタ取込` は「4. 診断する」に残す**
こちらは転換質を算出する診断機能を含むため。移すと診断タブから転換質算出が消える。

**③ 🔎 YouTube自動検索の結果に「DBに登録」ボタンを追加**
`searchYTSource` の結果テーブルに、既存 `registerCand({account, media:'YouTube', followers, conversion})` を呼ぶボタンを足す。S2d-2のX診断カードや `runYTBatch` と同じ形にそろえる。

## 未確定事項（実装時／初回実行時に確定）

- **`sort:'Top'` と `'Latest'` のどちらが候補発掘に向くか。** 実地検証は `Top` で行った。`Top` は反応が大きいツイートが集まる＝インフルエンサーが見つかりやすい一方、鮮度が落ちる可能性がある。初回運用で比較して決める（アクター入力を変えるだけで切替可能）
- **除外キーワードの実地強化。** S2d-2と同様、実データで誤除外・取りこぼしが出たらマーカーを追加する。設計時点の語彙は暫定
- **エンゲージ率の分母下限（100）の妥当性。** 実データを見て調整する
