## 1. 背景と課題

**受賞対象は商品・サービス単位だが、自動発掘はブランド単位で止まっている。**

設計書・運用ルールはいずれも商品単位を前提にしている:

| 根拠 | 内容 |
|---|---|
| 重複排除ルール（ランブック§2-4） | 「色違い・サイズ違い・香り違い＝同一対象」＝**商品バリエーションを束ねる粒度** |
| エントリーフォーム（form-spec） | **「商品URLまたはサービスURL」が必須**＝インバウンドは商品単位で入る |
| 2次審査（選出設計§2） | **お試し会** — ブランドは試せない。商品でなければ成立しない |
| 企業連絡（選出設計§2.4） | **商品サンプル**・画像素材の提供依頼＝具体的な商品が必要 |
| 受賞部門 | ベストコスメ賞／ベストスキンケア賞／**ベスト新商品賞** |

一方、TikTok共起タグによる自動発掘の実測（2026-07-27）では:

| カテゴリ | 実例 | 粒度 |
|---|---|---|
| エンタメ・スポット | 鬼滅の刃、江ノ島、cocotte cafe、弘大 | ✅ それ自体が受賞対象 |
| サービス・EC | SHEIN、Temu、Qoo10 | ✅ サービス自体が対象 |
| **美容・物販** | ロムアンド、キャンメイク、fwee、ケラスターゼ… | ❌ **13件中12件がブランド止まり** |
| 店舗チェーン | セブンイレブン、ファミマ、セリア | ❌ チェーン止まり |

→ **インバウンド（フォーム）は商品単位なのに、自動発掘だけブランド単位**という非対称が生じている。

## 2. 技術的な実現可能性（実測で検証済み・2026-07-28）

発掘済みブランド名でTikTokを再検索すると、共起タグに**実在の商品名が出る**ことを確認した:

| ブランド | 取れた商品名 |
|---|---|
| キャンメイク | クリーミータッチライナー／クリームチーク／プランぷくコーデアイズ／粘膜ライナー |
| ロムアンド | juicyflashlipoil（ジューシーフラッシュリップオイル）／틴트（ティント） |
| ケラスターゼ | グロスアブソリュ／ケラスターゼトリートメント |

ノイズ（韓国コスメ、美容師、ウォニョン、クリスマスプレゼント等）も混ざるため、**1段目と同じくClaude精選が必須**という構造も同じ。既存の `scripts/apify/discover_tiktok.js` が無変更で再利用できる。

## 3. 制約: 時間（設計を規定する最大要因）

1シードあたり実測**約35秒**。提案は20〜27件出るため、全件を提案時に解決すると**12分以上の追加**となり、既存の7〜8分と合わせて20分超。
発掘ジョブはCloud Run上でHTTPレスポンス返却後の非同期処理として走り、**タブを開いている間だけ生存**するため、20分超は現実的に破綻する。

→ **「提案と同時に商品まで一気に」は時間的に不可能。** 採用後に対象を絞って解決する（A-1方式）。

## 4. 方針（採用案 A-1）

**編集部が採用したものだけ、商品を解決する。**

- 実行対象が数件に絞られ、時間内に収まる
- 採用しないブランドの商品を調べる無駄がない
- 「編集部は探さず評価する／承認したものにだけ手をかける」という設計思想と一致

### 4.1 全体フロー

```
[既存・変更なし] 「候補を提案してもらう」→ ブランド/エンティティの提案
   ↓ 編集部がチェックして「採用」
[新規] カテゴリで分岐（needsProductResolution）
   ├─ 商品系カテゴリ
   │     ↓ 採用ブランドごとにTikTok再検索（既存 discover_tiktok.js を再利用）
   │     ↓ Claude精選「このブランドの具体的な商品はどれか」（新規 filter_products.js）
   │     ↓ 商品候補を提示 → 編集部がチェック（複数選択可）
   │     ↓ 登録（対象名＝商品名 / 企業名＝ブランド名）
   └─ 非商品系カテゴリ
         ↓ そのまま登録（＝現状の挙動を維持）
```

### 4.2 カテゴリ分岐（純粋関数 `needsProductResolution(category)`）

**商品解決が必要（true）**:
`コスメ` / `スキンケア` / `ヘアケア` / `ボディケア` / `フレグランス` / `食品・飲料` / `ライフスタイル雑貨` / `ファッション`

**不要（false）**:
`おでかけ・スポット` / `エンタメ・コンテンツ` / `その他` / 未知のカテゴリ（デフォルトfalse）

理由: 江ノ島・鬼滅の刃・cocotte cafe はそれ自体が受賞対象であり、商品解決をすると無意味な検索が走る。未知カテゴリは安全側に倒して解決しない（誤って時間を浪費しない）。

> 店舗チェーン（セブンイレブン／ファミマ／セリア）は `食品・飲料`・`ライフスタイル雑貨` に属するため
> **商品解決の対象**とする（確定方針）。「セブンイレブンの◯◯」まで落とす。
> チェーン自体を候補にしたい場合は §4.4 の逃げ道（ブランドのまま登録）を使う。

### 4.3 1ブランド複数商品（確定方針）

**複数の商品を、それぞれ別候補として登録できる。**
キャンメイクなら クリーミータッチライナー／クリームチーク／プランぷくコーデアイズ を個別の候補にできる。
同一ブランドの複数ヒット商品は、賞としては別々に競うべき対象であるため。
UIは提案リストと同じチェックボックス方式（複数選択可）。

### 4.4 商品が特定できなかった場合の逃げ道（必須）

マイナーブランドでは共起に商品名が出ないことがある。候補が失われるのを防ぐため、
**「商品が特定できませんでした。ブランドのまま登録しますか？」の選択肢を必ず残す**。
編集部が後から手で商品名・URLを補完できる。この逃げ道はチェーン自体を候補にしたい場合の受け皿も兼ねる。

### 4.5 時間の上限とローテーション

**1回の商品解決は10ブランドまで**（≒6分、実証済みの範囲内）。
超過分は**明示ログを出して次回に回す**（サイレント切り捨て禁止 — カバレッジ改修と同じ原則）。

## 5. コンポーネントと責務

| 単位 | 責務 | 依存 |
|---|---|---|
| `needsProductResolution(category)`（新規・純粋関数） | カテゴリが商品解決を要するか判定 | なし（テスト容易） |
| `resolveProducts(brands, onLog)`（新規） | 採用ブランド→TikTok再検索→Claude精選→商品候補を返す。**Notionには書かない** | discover_tiktok / filter_products |
| `scripts/ai/filter_products.js`（新規） | 「このブランドの具体的商品はどれか」をClaudeで判定 | Anthropic |
| `scripts/apify/discover_tiktok.js`（**無変更**） | 与えられたタグでTikTok共起タグを集計 | Apify |
| `POST /api/products/resolve`（新規） | 商品解決ジョブを起動（`job.resolved` を返す） | resolveProducts |
| `POST /api/candidates/bulk`（拡張） | `企業名` を受け取り登録できるようにする | notion.js |

**新規ファイル `award-signal-tool/lib/products.js` に分離する。**
`discover.js` は既に200行超であり、「シードからの発掘」と「ブランドからの商品解決」は責務が異なるため。

## 6. データの入り方（スキーマ変更なし）

候補プールDBには既に必要なフィールドが存在する。**スキーマ変更は不要。**

| フィールド | 入れる値 |
|---|---|
| `対象名`（title） | **商品名**（例: クリーミータッチライナー） |
| `企業名`（rich_text） | **ブランド名**（例: キャンメイク） |
| `カテゴリ`（select） | 1段目で判定済みのカテゴリ |
| `トレンドポイント`（rich_text） | 🔎自動生成の由来＋Claudeの判断理由 |
| `流入経路` / `段階` | 編集部リサーチ / 0次（既存 `createCandidate` のまま） |

`商品/サービスURL`・`価格`・`概要` は本設計では自動補完しない（編集部が企業連絡時に埋める。§7参照）。

## 7. スコープ外（YAGNI）

- 商品URL・価格・概要の自動取得（企業連絡フェーズで人が埋める運用が既にある）
- 商品ごとの実績スコア自動再取得（既存の「シグナル取得」機能で別途行える）
- ブランド→商品の自動登録（**承認後のみ登録の原則は変えない**）
- フィードバックループの半自動化（[カバレッジ設計§9](2026-07-27-trepo-award-seed-coverage-design.md)の別テーマ）

## 8. テスト

- **`needsProductResolution` の単体テスト**（ネットワーク不要）:
  - 商品系8カテゴリすべてで true
  - 非商品系（おでかけ・スポット／エンタメ・コンテンツ／その他）で false
  - 未知カテゴリ・空文字・undefined で false（安全側）
- **`resolveProducts` の上限・分岐テスト**（Apifyはモック）:
  - 10ブランド超で超過分が deferred に入り、ログに出る
  - 非商品系カテゴリのブランドは解決対象から除外される
  - 商品が0件のブランドは「特定できず」として結果に含まれる（消えない）
- **結合（手動・実キー）**: キャンメイク等の実ブランドで `resolveProducts` を1回流し、
  商品名が返ること・ノイズが落ちていることを確認（§2の実測と同等）。

## 9. リスクと対処

| リスク | 対処 |
|---|---|
| 商品名が共起に出ないブランドがある | §4.4 の逃げ道（ブランドのまま登録）で候補を失わない |
| 採用数が多いと時間超過 | §4.5 の10ブランド上限＋次回ローテーション |
| Claudeが商品でないものを商品と誤判定 | 提案止まりで人が承認するため、DBは汚れない |
| 同じ商品が別表記で重複登録される | 既存候補との重複チェック（`adoptCandidates` の既存ロジック）を通す |
| 採用フローが2段階になりUXが複雑化 | 非商品系は従来通り即登録。2段階になるのは商品系のみ |
