# 気づきワードサイクル — Track A（標準化3択アンケート）取込 設計書

作成: 2026-08-16
関連: [Phase3スライス2（Pamun取込）](2026-07-16-kizuki-word-cycle-phase3-slice2-pamun-ingest.md) / [運用手順書](../../deploy/phase3-slice2-pamun-ingest-runbook.md)

## なぜ作るか

Phase3スライス2（Track B）を実データで動かした結果、**15ワード全ての購買意向共感率が0%**になった。
分類の失敗ではない。Pamunの事後アンケートは「商品の感想」しか聞いておらず、自由記述に
「買いたい／使い続けたい」に相当する記述がほぼ現れないため、意向として数えられる回答が存在しない。

結果として件数（言及の広がり）は取れるが、**設計の主役である「件数は高いが共感率が低い＝虚栄ワード」の
炙り出しが機能しない**。Track A は意向を設問構造で直接聞くことでこれを構造的に解決する。

## 設問形（スライス2設計書で確定済み）

> **Q. 「〇〇（気づきワードの言い回し）」について、あなたに一番近いものは？ [word_id]**
> 1. ピンとこない／当てはまらない … 分母のみ
> 2. 共感する（でも購入の決め手ではない） … 件数 +1、意向 0 ＝ **虚栄反応の受け皿**
> 3. 共感するし、これがあるから買いたい／使い続けたい … 件数 +1、意向 +1

集計は決定的（LLM不要）。件数 = ②③、意向 = ③、共感率 = ③ ÷ n。
「虚栄反応は除外」が設問構造で担保される（可愛い等は②に落ち③に上がらない）。

## 運用上の決定

| 論点 | 決定 | 理由 |
|---|---|---|
| 誰に聞くか | **Pamunモニターの事後アンケートに組み込む** | 意向が測れない問題を直接解消する。同じ回答者から trackB と trackA の両方が取れる |
| 列と word_id の紐づけ | **設問文の末尾に `[word_id]` を入れる** | 文言を随時修正する運用のため。文言一致だと修正のたびに突合が壊れ、該当ワードだけ静かに0件になる |
| どのワードを設問化するか | **台帳の `status='モニター'` の行** | 選択肢は既存。「モニターに掛けると決めたワード」という意味そのもの。新しい仕組みを増やさず人の判断で握れる |

## アーキテクチャ

Track A は Pamun の事後アンケートに同居するため、**回答シートは Track B と同じ**。
`Pamun取込マッピング` の1行を2つの取込が共有する。

```
Pamun取込マッピング（1行 = 1施策）
  ├─ pamun_ingest.js   自由記述 → LLM分類      → source=trackB
  └─ tracka_ingest.js  3択      → 決定的に集計 → source=trackA   ← 本設計
                                    ↓
                        モニターシグナル
                          （ledger-store の source優先ピックで trackA が採用される）
```

LLMを使わないため `tracka_ingest` は速く・安く・再現的。マッピングの追加列は不要。

## 構成要素

### 1. `scripts/kizuki/tracka_questions.js` — 設問生成（読み取りのみ）

台帳から `status='モニター'` かつ指定 case の行を引き、フォームに貼り付ける設問テキストを出力する。

- 出力は標準出力のみ。シートには一切書き込まない
- 件数が **5〜8件の範囲外なら警告**（設問数＝ワード数のため、超えると回答負担で離脱する）
- 設問文の末尾に `[word_id]` を付ける

### 2. `lib/kizuki/tracka-ingest.js` — 純粋関数（新規）

| 関数 | 責務 |
|---|---|
| `detectWordColumns(headerRow)` | 見出しから `[wNNN]` を抽出し `[{index, wordId}]` を返す |
| `parseChoice(value)` | 選択肢の文言から `1\|2\|3` を取り出す。取れなければ `null` |
| `parseTrackAResponses(rows)` | 回答者ごとに `[{wordId, choice}]` を組み立てる。既存 `tallyTrackA` にそのまま渡せる形 |

`tallyTrackA` / `buildReviewSignalRows` は既存のものを使う。**集計ロジックは新規に書かない。**

### 3. `scripts/kizuki/tracka_ingest.js` — バッチ

マッピング → 回答シート → `parseTrackAResponses` → `tallyTrackA` → `buildReviewSignalRows(source=trackA)` → upsert。
upsertキーは `(word_id, campaign_id, source)` で `pamun_ingest` と共通。手入力行・trackB行は触らない。

## 織り込む失敗モード

いずれも例外を出さずに数値だけ狂う類。実装時に回帰テストとして固定する。

| 失敗モード | 対処 |
|---|---|
| **`choice` が文字列のまま** | `tallyTrackA` は `a.choice !== 2 && a.choice !== 3` で厳密比較する。`'3'` を渡すと全ワードが0件に潰れ、例外も出ない。`parseChoice` は**必ず number を返す** |
| **選択肢の表記ゆれ** | Googleフォームは選択肢の文言全体を返す（`② 共感する…`）。全角丸数字 `①②③` と先頭の半角数字の両方を受ける |
| **名簿行による分母水増し** | 設問列に1つも回答が無い行は回答者に数えない（Track B で踏んだのと同じ対策） |
| **列の突合失敗** | 台帳にあるのに設問列が見つからないワードは、黙って0件にせず**警告として出す**。文言修正でズレた場合にここで気づける |

## テスト方針

- 純粋関数は TDD。上表の失敗モードをすべて回帰として固定する
- スクリプトは既存の配線テストと同じ方式（子プロセスで本物のまま起動し `lib/sheets` だけ差し替え）
- 実装後に変異テストで捕捉を確認する

## やらないこと

- Googleフォームの自動生成（Forms API 未有効・権限外。設問テキストを出すところまで）
- `Pamun取込マッピング` へのマッピング列追加（回答シートが同じなので不要）
- 集計ロジックの再実装（`tallyTrackA` は実装・テスト済み）
