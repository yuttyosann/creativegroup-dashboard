# Trepoトレンド大賞2026 実績スコア調査ランブック（Phase 1）

- 作成日: 2026-06-17
- 親設計書: `2026-06-16-trepo-trend-award-selection-design.md`（§3.2）
- 位置づけ: 編集部リサーチSOP（`trepo-award-research-sop.md`）の**データファースト版**。
  「編集部が主観で探す」のをやめ、**客観データで候補を出し、編集部は得点を足すだけ**にする。
- スコープ: 今サイクル（1回目）を手動〜半自動で回し切る Phase 1。BigQuery自動化は Phase 2。

---

## 0. 全体の流れ（3層）

```
Layer 1 候補生成（客観）   公開ランキング＋急上昇シグナル → 候補ロングリスト（Notion候補プールDB）
Layer 2 実績スコア付与（客観・半自動）  ショートリストに Apify/Trends を当て、5シグナルを1〜5に正規化
Layer 3 編集得点（主観）   スコアカードシートで編集4項目を加点
```

> 編集部の役割は「発見」ではなく「評価」。候補は人の主観ゼロで出す。

## 1. 対象ランキング源（カテゴリ別・確定）

各カテゴリで下記の公開ソース上位を拾い、候補プールDBに投入する。**ランキング順位は「売上実績」の代理指標**として記録する。

| カテゴリ | 主なランキング源 |
|---|---|
| コスメ／スキンケア／ヘアケア／ボディケア／フレグランス | @cosme（ベストコスメ・週間ランキング）／LIPSランキング／Qoo10メガ割ランキング／楽天ビューティ |
| 食品・飲料 | コンビニ各社の新商品／話題商品、楽天グルメランキング、SNS（#コンビニスイーツ 等）、食べログスイーツ |
| ライフスタイル雑貨 | 楽天／Amazonランキング、3COINS・ロフト・PLAZAの話題商品 |
| ファッション | ZOZOTOWNランキング、WEAR、GU・SHEIN等の話題アイテム |
| おでかけ・スポット | SNS（#〇〇カフェ／#映えスポット）、じゃらん、Googleトレンド |
| エンタメ・コンテンツ | YouTube急上昇、TikTok急上昇、各サブスクチャート、Xトレンド |
| 横断（全カテゴリ・無料で強力） | **TikTok Creative Center**（急上昇ハッシュタグ・楽曲）、**Googleトレンド急上昇**、Xトレンド |

> TikTok Creative Center は**無料・客観・Z世代の実トレンド**を直接拾えるので、手動スイープの主軸に置く。

### ⚠️ 重要な知見: Google Trendsは「候補発見」には使えない（2026-07 検証）

| モード | 結果 |
|---|---|
| `discover`（急上昇検索） | ❌ **404** — Googleが旧trending APIを廃止（pytrends非対応） |
| `related`（急上昇関連クエリ） | ❌ **429** — 関連クエリのエンドポイントは制限が特に厳しい |
| `score`（検索の伸び） | ✅ 動作（＝**採点用途は問題なし**） |

→ **Trendsは「既知の候補を採点」はできるが「新しい候補を発見」はできない。**
候補の自動生成は **TikTok（Apify）＋ Claude精選** を主軸にする（下記）。

### 自動の候補生成パイプライン（TikTok × Claude）

```
シード設定DBのハッシュタグ
   ↓ node scripts/apify/discover_tiktok.js   … 共起ハッシュタグを集計して発掘
共起タグ（総称語・persona語・表記ゆれのノイズが多い）
   ↓ node scripts/ai/filter_candidates.js    … Claudeが精選・カテゴリ補正・表記統一
精選された候補  → 編集部が承認して候補プールDBへ
```

- **なぜClaude精選が必須か**: 生の共起タグには `オタク` `vlog` `量産型` `東京` `パン` のような
  総称語・persona語・プラットフォーム定型が大量に混ざり、除外リストでは追いつかない。
  またシード由来のカテゴリ継承は誤りやすい（`#聖地巡礼`由来のアニメが「おでかけ」になる）。
  実測: ノイズ33件 → 精選16件（カテゴリ正確・`rezero/リゼロ`等の表記ゆれも統合）。
- **自動登録はしない**: 精選後も編集部が承認してから候補プールDBに入れる
  （設計思想「編集部は探さず"評価"する」に合致し、DBがノイズで汚れない）。

**ツールでの回し方（https://award.trepo.jp・実装済み）**:
1. 「🔎 候補を提案してもらう」を押す（発掘＋精選で数分かかる。この時点ではDBに何も入らない）
2. 「候補の提案」カードに精選結果が出る。Claudeの判断理由を見ながら採用するものにチェック
3. 「チェックした候補を登録」→ 選んだ候補だけ `流入経路=編集部リサーチ` / `段階=0次` で登録される
4. 既にDBにある対象は自動でスキップされる（重複登録の心配なし）

### 1-2. TikTok取り込み（ハイブリッド方式）

TikTokは「発見」と「定量化」で取得手段を分ける。

| 役割 | 方法 | ツール |
|---|---|---|
| **発見（Layer 1）** | Creative Centerを週1で手動スイープ | 手動（下記SOP） |
| **定量化（Layer 2）** | ハッシュタグ/キーワードの再生数・エンゲージを取得 | `node scripts/apify/fetch_tiktok.js` |

> Creative Centerの「急上昇ハッシュタグ一覧」には安定した無料APIが無いため、発見は手動が最も堅い。
> 数値化だけApifyで自動化する。

**Creative Center 手動スイープ SOP（週1）:**
1. https://ads.tiktok.com/business/creativecenter/ を開く（無料TikTokアカウントでログイン）
2. 地域＝**日本**、期間＝**直近7日/30日**で絞る
3. 次の3面を確認し、Trepo読者（Z世代女性）に刺さりそうな項目を拾う:
   - **Trending Hashtags**（ジャンル横断の本丸）
   - **Trending Songs**（楽曲発の商品・コラボの兆し）
   - **Top Products / Trend Discovery**（提供地域で見られる場合）
4. 拾った対象を候補プールDBに `流入経路 = 編集部リサーチ` で追加。ハッシュタグ名を `SNS_根拠` にメモ。
5. 後で `fetch_tiktok.js` にそのハッシュタグを渡し、`SNS話題量_点` を数値化。

## 2. 候補ロングリストの作り方（Layer 1）

**置き場所**: Notion「Trepo編集部」配下の「Trepoトレンド大賞2026 候補プール」DB（`3832a9c9-20f7-81ad-a21e-fee38dfd4b8c`）。新規DBは作らない。

手順:
1. リサーチ期間（6/18〜8/31）に、§1の各ソースの上位を候補プールDBへ追加（`流入経路 = 編集部リサーチ`）。
2. 最低限の必須記録: `対象名` / `カテゴリ` / `商品・サービスURL`。
3. **ランキング出典＋順位を `売上_根拠` 列に記録**（例: 「@cosme週間1位 / 6月3週」）＝売上代理指標のエビデンス。
4. 重複排除ルール（フォーム注意事項と統一）:
   - 色違い・サイズ違い・香り違い＝**同一対象**（1件にまとめる）
   - 用途・形状が異なる＝**別対象**
5. インバウンド（フォーム応募）は **`scripts/trepo_award_form_to_notion.gs`** が onFormSubmit で
   自動的に同じDBへ `流入経路=インバウンド`・`段階=0次` で登録する（週次レビューで内容を確認）。

**役割分担**（探す人とデータを当てる人を分ける）:
- 候補拾い: 美容班／食品・生活班／カルチャー班でソースを分担
- データ取得: データ担当1〜2名が Apify/Trends を回す（編集部全員ではない）

## 3. ショートリストへの実績スコア付与（Layer 2）

コストと工数を抑えるため、**全件ではなくショートリストにだけデータを当てる**。

1. ロングリスト → 0次（形式要件チェックリスト）でふるい → **カテゴリ別上位20〜30件**をショートリスト化。
2. ショートリストの各候補に、5シグナルを取得して `_点`（1〜5）＋`_根拠` を埋める。

### シグナル別 取得手順

| シグナル | 取得方法 | 候補プールDBの記入先 |
|---|---|---|
| SNS話題量 | `node scripts/apify/fetch_instagram.js <ハッシュタグ/アカウント>` で投稿量・エンゲージ取得。または TikTok Creative Center で該当ハッシュタグの再生数を確認 | `SNS話題量_点` / `SNS_根拠` |
| 検索の伸び | Google Trends に候補名を入力し、相対伸び率・急上昇を確認（Phase 2でpytrends自動化） | `検索の伸び_点` / `検索_根拠` |
| インフル反響 | `node scripts/youtube/fetch_channel.js <ハンドル>` ＋ Apify IG で言及インフルの数・規模を確認 | `インフル反響_点` / `インフル_根拠` |
| メディア掲載 | `python3 scripts/media/fetch_media.py "<候補名>"`（Google News＋PR TIMESの掲載件数→1〜5） | `メディア掲載_点` / `メディア_根拠` |
| 売上実績 | §2で記録済みのランキング順位を採点に反映（実売は非公開のため代理） | `売上実績_点` / `売上_根拠` |

### 1〜5への正規化（データアンカー v0.1）

- 原則: **候補プール内のパーセンタイルで5分位** → 上位20%=5点 … 下位20%=1点。
- データが揃わないシグナルは **N/A（空欄）**。スコアカードシートが該当項目のみで正規化する。
- 簡易しきい値で代用する場合の初期案（v0.1・次年度較正前提）:
  - SNS話題量: 関連投稿/再生が突出=5 ／ 多い=4 ／ 中=3 ／ 少=2 ／ ごく僅か=1
  - 検索の伸び: 急上昇=5 ／ 明確に増=4 ／ 横ばい=3 ／ 弱=2 ／ なし=1
- **エビデンス必須**: `_点` を入れたら必ず `_根拠` にリンク/数値を残す（空の点は無効）。
