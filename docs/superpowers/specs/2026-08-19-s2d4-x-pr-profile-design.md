# S2d-4: X候補のPR実績・ジャンル診断 設計書

**日付:** 2026-08-19
**関連:** S2d-2（X転換質診断）／S2d-3（X候補検索）
**ステータス:** 設計

---

## 背景

S2d-3でX候補の母集団は作れるようになった（キーワード検索→エンゲージ率順→候補DB登録）。しかし**候補を選別する材料が足りない**。フォロワー数とエンゲージ率だけでは「この人に商品を任せてよいか」が判断できない。

実運用の初回検索でユーザーから3つの要望が出た。

- PR案件をどのくらいやっているか
- PR投稿のエンゲージメント
- ジャンル

本設計はこれに応える。あわせて、候補DBに用意されていながら**ずっと空のままだった `ジャンル`・`PRエンゲージ%` 列を初めて埋める**。

---

## 実測で判明したこと（設計の前提）

設計にあたり実データを2度検証し、**当初の想定を2回とも覆した**。この経緯は判断の根拠として重要なので記録する。

### ① PR表記はハッシュタグではなく「裸のPR」

S2d-2から使っている `isPRPost`（`#pr` / `#ad` / `#提供` / `タイアップ` / `案件` 等の部分一致）は、実データでほぼ機能しない。

- 厳密なハッシュタグ形式（`#PR`等）は**2アカウントとも0件**
- 一方 `提供` は「熊本地震の支援物資を提供」に、`ad` は成分名 `Cellad*ad*ix` に誤反応

実際の表記は**本文中の独立した「PR」**だった。文末・文頭・`【PR】`・`【PR/ブランド名】`・`👍PR` など。

判定を「URL除去後、前後が英字でない独立した `PR`」に変えたところ、実測は次のとおり。

| アカウント | ツイート数 | PR判定 | 実際の中身 |
|---|---|---|---|
| @marunouchi__ol_ | 63 | 13件（21%） | `【PR/アスタリフト】` `【PR】エイトザタラソSR` |
| @kaori_online | 115 | 39件（34%） | `【PR_オルビス】` `👍PR` `#PR #水光肌の作り方` |

**誤検出ゼロ、取りこぼしなし。** この判定は実用に足る。

### ② 「有料パートナーシップ」ラベルはAPIで取れない

X公式のPaid Partnershipラベルは画面には出るが、Apifyのレスポンスには `partnership` / `paid` / `sponsor` 等の痕跡が一切ない（実レスポンスを全文検索して確認）。**テキスト判定が唯一の手段**。

### ③ PR投稿でエンゲージが激減する例が実在する

@marunouchi__ol_（フォロワー73万）の実測値。

- PR投稿のいいね：185 / 157 / 528 / 367
- 非PR投稿のいいね：26,232 / 23,439 / 14,101

**PR投稿になった瞬間に反応が2桁落ちる。** フォロワー数だけを見て起用すると失敗する典型例であり、この落差こそが最も価値のある判断材料である。よって本設計の**主指標はPR投稿と非PR投稿のエンゲージ率の比較**とする。

### ④ 商品紹介率は識別力がない（不採用）

当初「商品紹介投稿の割合をClaudeが判定する」案を検討したが、カタカナ商品名を含む投稿は**8〜9割**で、美容アカウントならほぼ全員が該当し選別に使えない。明示PR判定が機能する以上、コストをかけて足す意味がないため**採用しない**（YAGNI）。

## ゴール / 非ゴール

**ゴール**

- 明示PR投稿の本数と割合を出す
- PR投稿と非PR投稿のエンゲージ率を比較し、「PRで落ちる人」を可視化する
- ジャンルを固定カテゴリ1つで判定し、候補DBで絞り込めるようにする
- 候補DBの `ジャンル`・`PRエンゲージ%` 列を埋める
- 既存の「🐦 X転換質診断」の1回の実行にまとめる（別操作を増やさない）

**非ゴール**

- PR表記のない案件を推測すること（表記なしの案件は存在しうるが、推測は根拠が薄く数字の信頼性を損なう）
- 商品紹介率の算出（上記④の理由で不採用）
- YouTube/Instagram への同機能の展開（Xで有効性を確認してから判断する）
- 過去全期間の集計（取得上限があるため直近のみ。後述）

## 測る指標

| 指標 | 定義 | 格納先 |
|---|---|---|
| PR投稿数 | 明示PR判定に該当したツイート数 | 表示のみ |
| PR率 | PR投稿数 ÷ 全ツイート数 × 100 | 表示のみ |

**「全ツイート」の定義:** 本人の**非リプライ投稿のみ**を分母とする。他人への返信（リプライ）は投稿活動の性質が違い、PR投稿はまず含まれないため、分母に入れるとPR率が不当に低く出る。実測の21%・34%もこの定義で算出している。リツイートも分母から除く（本人の発信ではないため）。
| **PRエンゲージ率** | PR投稿の平均(いいね+RT) ÷ フォロワー × 100 | 候補DB `prEngage` |
| 非PRエンゲージ率 | 非PR投稿の平均(いいね+RT) ÷ フォロワー × 100 | 表示のみ |
| **PR係数** | PRエンゲージ率 ÷ 非PRエンゲージ率 × 100（%） | 表示のみ |
| ジャンル | 固定8カテゴリから1つ | 候補DB `genre` |

**PR係数の読み方:** 100%なら「PRでも通常と同じだけ反応がある」、50%なら半減、@marunouchi__ol_ のようなケースでは数%になる。**この数値が低い候補は、フォロワー数が大きくても起用効果が薄い。**

エンゲージ率の定義はS2d-3と揃える（`(いいね+RT) ÷ フォロワー × 100`、重み付けなし）。内訳は全て返し、後から別定義で再集計できるようにする。

**`prEngage` 列の意味の訂正:** S2d-3では検索時の一般エンゲージ率を暫定的にこの列へ入れていた。列名「PRエンゲージ%」の本来の意味はPR投稿のエンゲージ率であり、S2d-4の値が正しい。**S2d-4の診断を実行したら上書きする**（暫定値より精度が高いため）。

**サンプル不足の扱い:** PR投稿が3件未満のときは平均が不安定なので、値は返しつつ `lowPrSample: true` を付けてUIに⚠️を出す。S2d-2の `lowSample` と同じ方針。

**較正スタンス:** S2d-2・S2d-3と同じく**X内の相対比較専用**。YouTube/IGの指標とは較正していないため媒体をまたいで並べない。UIに明記する。

## ジャンル判定

**固定8カテゴリから1つだけ選ぶ。**

`スキンケア` / `メイク` / `美容医療` / `ヘアケア` / `ボディケア` / `ファッション` / `ライフスタイル` / `その他`

自由記述にしない理由は、候補DBでの絞り込み・並べ替えに使うため。表記がブレると検索に使えない。

判定はClaude（`claude-sonnet-4-6`）。入力はプロフィール文＋直近ツイート20件の本文。**転換質判定とは別の呼び出しに分ける。** 入力の性質（リプライ群 vs プロフィール＋投稿）が大きく異なり、1つのプロンプトに混ぜると双方の精度が落ちるため。ジャンル判定は入力が小さく、追加は10〜20秒程度。

カテゴリ外と判断した場合は `その他` を返す。無理に既存カテゴリへ寄せない。

## 取得方式（重要な変更）

**現状の問題:** S2d-2の `fetch_x_replies.js` は `minReplyCount: 5` で「リプライ5件以上の投稿」に絞って取得している。しかし**PR投稿はリプライが少なく、この条件では漏れる**（実測でPR投稿のいいねは185〜528、リプライはそれ以下）。この条件のままではPR率が正しく出ない。

**変更:**

- `minReplyCount` を**撤廃**し、直近の投稿を条件なしで取得する
- `maxItems` を **300 → 500** に引き上げる（本人のリプライが枠を消費するため。実測では300件取得時にツイートは109件だった）
- 転換質診断用のリプライ数フィルタは**取得後にコード側で行う**（従来と同じ結果になる）

**コスト:** 1アカウントあたり約30円（従来は約15円）。転換質診断は元々1件ずつ実行する設計なので、総額への影響は限定的。

**期間の限界:** 90日を指定しても500件上限に達すると期間が短くなる（実測では300件で約45日分）。**「直近◯件・◯日分」を結果に明示**し、期間が指定より短い場合はその旨を返す。集計期間が候補ごとに違うことを隠さない。

## アーキテクチャ

S2d-2/S2d-3の構造を踏襲する。新しいインフラは増やさない。

```
候補DBタブ「🐦 X転換質診断」（既存カードを拡張）
   │  POST /api/cockpit/x-intent  { account }   ← 既存エンドポイントを拡張
   ▼
cockpit-server.js
   │ ① runScriptJson → scripts/apify/fetch_x_replies.js（取得条件を変更）
   │      └ lib/x-pr-filter.js（純粋関数）でPR/非PRに分割・エンゲージ集計
   │ ② Claude: 転換質判定（既存 lib/x-intent-prompt.js）
   │ ③ Claude: ジャンル判定（新規 lib/x-genre-prompt.js）
   ▼
結果表示（転換質＋PR実績＋ジャンル）→「DBに反映」→ conversion / prEngage / genre
```

## データフロー

1. 候補DBタブでX候補を選び「選択した候補を診断」（既存UI）
2. `POST /api/cockpit/x-intent { account }`
3. `fetch_x_replies.js` が直近投稿＋リプライを取得（条件変更済み）
4. `lib/x-pr-filter.js` がPR/非PRに分割し、それぞれのエンゲージ率とPR係数を算出
5. Claude① 転換質判定（既存）
6. Claude② ジャンル判定（新規）
7. 結果をまとめて返す
8. 「DBに反映」で `conversion` / `prEngage` / `genre` を候補DBへupsert

## エラーハンドリング

S2d-2と同じく、**段ごとに切り分けて返す**（どこで失敗したか運用者が分かるように）。

| 状況 | 挙動 |
|---|---|
| `APIFY_TOKEN` / `ANTHROPIC_API_KEY` 未設定 | 400（既存と同じ） |
| Apify取得失敗 | 500＋取得段のエラーと明示（既存と同じ） |
| PR投稿0件 | `prEngage: null` / `prRate: 0`。「PR投稿なし（表記のない案件は検出できません）」と注記 |
| 非PR投稿0件 | PR係数を `null`（比較対象がないため） |
| PR投稿1〜2件 | 値は返すが `lowPrSample: true` でUIに⚠️ |
| ジャンル判定失敗 | `genre: null`。**転換質とPR指標は返す**（ジャンルだけのために全体を失敗させない） |
| 取得が上限に達した | `truncated: true` と実際の集計期間を返す |

## テスト方針

**単体テスト（`node:test`）**

`lib/x-pr-filter.js`
- 実データ由来のPR表記を検出：`【PR/アスタリフト】` `【PR】エイトザタラソSR` `👍PR`（文末） `【PR_オルビス】` `#PR #水光肌の作り方`
- 英単語内の `pr` を誤検出しない：`product` `press` `April` `surprise`
- URL内の文字列を誤検出しない（判定前にURL除去）
- PR/非PRの分割とそれぞれの平均エンゲージ率
- PR係数：通常計算／非PR0件で `null`／フォロワー0でゼロ除算しない
- `lowPrSample`：PR投稿3件未満で `true`

`lib/x-genre-prompt.js`
- 8カテゴリが漏れなくプロンプトに含まれる
- カテゴリ外は「その他」を選ぶよう指示されている
- 入力が空のときエラーを投げる

**手動確認（デプロイ後）**
- @marunouchi__ol_ を診断し、PR率21%前後・PR係数が著しく低い値になること（実測と整合するか）
- @kaori_online を診断し、PR率34%前後になること
- ジャンルが妥当か目視
- 「DBに反映」で候補DBの `ジャンル`・`PRエンゲージ%` が埋まること

## 未確定事項（実装時／初回実行時に確定）

- **PR表記の網羅性。** 実測2アカウントでは裸の `PR` で足りたが、`ＰＲ`（全角）・`Ad` 単独・「タイアップ」明記など他の書き方が出る可能性がある。初回運用で取りこぼしが見つかったらマーカーを追加する（S2d-3のマーカー調整と同じ運用）
- **PR係数の判断基準。** 何%以下を「PRで落ちる」と見なすかは実データが貯まってから決める。当面は数値をそのまま表示し、閾値による色分けは行わない（未検証の閾値を入れない）
- **`maxItems: 500` の妥当性。** 多投稿アカウントでは依然として期間が短くなる。実運用で不足するようなら引き上げるが、コストと相談する
- **ジャンル8カテゴリの粒度。** コスメ案件に寄せた分類のため、他ジャンルの案件が増えたら見直す
